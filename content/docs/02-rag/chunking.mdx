## Why This Matters

A RAG system can only answer from the text its retriever finds. And the retriever never searches your documents. It searches your **chunks**, the pieces you cut the documents into before indexing them. If a chunk is too big, it mixes five topics and matches every query weakly. If it's too small, the answer is split across two chunks and neither one is enough. If the PDF's page header ("Company X — Confidential") is inside every chunk, it pollutes every search.

Chunking sounds boring, and that's why teams skip it. But research shows it matters. Chroma's 2024 report *Evaluating Chunking Strategies for Retrieval* found that the chunking strategy alone changed retrieval recall by up to 9%. It also found that a popular default, 800-token chunks with 400-token overlap, scored poorly on its efficiency metrics. Anthropic's *Contextual Retrieval* study (Sept 2024) showed that adding a little context to each chunk cut retrieval failures by 35%, and by 49% when combined with keyword search.

By the end of this lesson you will be able to:

- load Markdown, text and PDF files into clean text with metadata,
- remove PDF noise such as running headers, footers and broken hyphenation,
- write a token-aware, structure-aware chunker with overlap and stable IDs,
- **measure** which chunking setup works for your documents, instead of guessing.

## The Ingestion Pipeline

Every RAG system has the same five steps before the first question is asked:

| Step | What happens | What goes wrong if you skip it |
|---|---|---|
| **1. Load** | Read files (PDF, Markdown, HTML, DOCX) into text | Tables and columns come out scrambled |
| **2. Clean** | Fix whitespace, hyphenation, headers and footers | Noise in every chunk, broken words that never match |
| **3. Chunk** | Split into pieces of a sensible size along natural boundaries | Answers cut in half, or buried in huge chunks |
| **4. Enrich** | Add metadata (source, page, section) and a short context header | No citations, no filtering, chunks that make no sense alone |
| **5. Index** | Embed and store each chunk with a stable ID | Duplicates every time you re-ingest |

This lesson covers steps 1–4 and prepares step 5. Embedding and storing chunks are covered in [Vector Databases](/docs/02-rag/vector-dbs).

## Chunking Strategies at a Glance

| Strategy | How it splits | Good for |
|---|---|---|
| **Fixed-size** | Every *N* tokens, no matter what | Quick baselines; uniform text like logs |
| **Recursive** | Paragraphs first, then lines, then sentences, then words, only as far as needed | Most prose. A strong default |
| **Structure-aware** | Along headings, sections, pages or code blocks, keeping the heading path | Docs, handbooks, Markdown, HTML, contracts |
| **Semantic** | Where the meaning changes, using embeddings | Long unstructured text with topic shifts |
| **LLM-based** | An LLM decides the boundaries | High-value corpora where recall matters most (expensive) |

In Chroma's tests, a plain **recursive splitter with 200-token chunks and no overlap** did consistently well across metrics, even though it was not the single best on recall. That is the default we'll build: recursive and token-aware, plus structure-awareness, because real documents have headings.

## Hands-On: Load and Clean

All code below was run with Python 3.12, `pypdf` 7.1, `tiktoken` 0.14 and `rank_bm25` 0.2.2.

```bash
pip install pypdf tiktoken rank_bm25
```

Our sample corpus is a fictional company's `handbook.md` (plans, billing, limits, support) and a two-page `security.pdf` whose pages repeat the header "Nimbus Cloud - Confidential" and the footer "Page 1 of 2".

```python
# ingest.py — load .md/.txt/.pdf files into clean text with metadata
import re
from collections import Counter
from dataclasses import dataclass, field
from pathlib import Path

from pypdf import PdfReader


@dataclass
class Document:
    text: str
    source: str
    metadata: dict = field(default_factory=dict)


def clean(text: str) -> str:
    text = text.replace("\r\n", "\n").replace(" ", " ")
    text = re.sub(r"(\w)-\n(\w)", r"\1\2", text)   # join words hyphenated across lines
    text = re.sub(r"[ \t]+", " ", text)            # collapse runs of spaces
    text = re.sub(r"\n{3,}", "\n\n", text)         # keep paragraph breaks, drop extra blank lines
    return text.strip()


def norm(line: str) -> str:
    return re.sub(r"\d+", "#", line.strip())       # "Page 1 of 2" and "Page 2 of 2" -> same key


def drop_repeated_lines(pages: list[str], min_share: float = 0.6) -> list[str]:
    """Remove running headers/footers: short lines that appear on most pages."""
    counts = Counter(norm(l) for p in pages for l in set(p.splitlines()) if 0 < len(l.strip()) < 80)
    repeated = {line for line, n in counts.items() if n >= max(2, min_share * len(pages))}
    return ["\n".join(l for l in p.splitlines() if norm(l) not in repeated) for p in pages]


def load(path: Path) -> list[Document]:
    if path.suffix.lower() == ".pdf":
        pages = [page.extract_text() or "" for page in PdfReader(path).pages]
        pages = drop_repeated_lines(pages)
        return [Document(clean(t), path.name, {"page": i}) for i, t in enumerate(pages, 1) if t.strip()]
    return [Document(clean(path.read_text("utf-8")), path.name, {})]


def load_folder(folder: str) -> list[Document]:
    docs = []
    for path in sorted(Path(folder).rglob("*")):
        if path.suffix.lower() in {".md", ".txt", ".pdf"}:
            docs.extend(load(path))
    return docs


if __name__ == "__main__":
    for d in load_folder("docs"):
        print(d.source, d.metadata, len(d.text), "chars |", d.text[:60].replace("\n", " "))
```

The PDF page after cleaning. The header and the "Page 1 of 2" footer are gone, and the word the PDF broke across two lines ("rota-" / "ted") is whole again:

```text
Security Policy
All customer data is encrypted at rest with AES-256. Encryption keys are rotated every 90 days. ...
```

Two details worth copying:

- **One `Document` per PDF page.** Keeping the page number means every answer can cite "security.pdf, page 2".
- **Headers and footers are found, not hard-coded.** A short line that appears on most pages (with digits normalised) is almost always page furniture.

> **Real PDFs are harder.** `pypdf` reads the text layer. Scanned PDFs have none, so you need OCR. Multi-column layouts and tables may come out in the wrong order. For those, use a layout-aware parser and *always look at the extracted text* before you index it.

## Hands-On: A Token-Aware, Structure-Aware Chunker

Models and embedding APIs count **tokens**, not characters, so we measure chunk size in tokens with `tiktoken`.

```python
# chunker.py — token-aware, structure-aware chunking with metadata and stable IDs
import hashlib
import re
from dataclasses import dataclass

import tiktoken

from ingest import Document

enc = tiktoken.get_encoding("o200k_base")
SEPARATORS = [r"\n\n", r"\n", r"(?<=[.!?])\s+", r"\s+"]  # paragraph -> line -> sentence -> word


def n_tokens(text: str) -> int:
    return len(enc.encode(text))


def split_text(text: str, max_tokens: int, seps: list[str] = SEPARATORS) -> list[str]:
    """Split on the biggest natural boundary first; go finer only for pieces that are still too long."""
    if n_tokens(text) <= max_tokens:
        return [text]
    if not seps:  # one giant "word": cut by tokens
        ids = enc.encode(text)
        return [enc.decode(ids[i:i + max_tokens]) for i in range(0, len(ids), max_tokens)]
    pieces = []
    for part in re.split(seps[0], text):
        if part.strip():
            pieces.extend(split_text(part.strip(), max_tokens, seps[1:]))
    return pieces


def merge(pieces: list[str], max_tokens: int, overlap: int) -> list[str]:
    """Pack small pieces into chunks of up to max_tokens, repeating ~overlap tokens between chunks."""
    chunks, current = [], []
    for piece in pieces:
        if current and n_tokens(" ".join(current + [piece])) > max_tokens:
            chunks.append(" ".join(current))
            tail = []
            while current and n_tokens(" ".join([current[-1]] + tail)) <= overlap:
                tail.insert(0, current.pop())
            current = tail
        current.append(piece)
    if current:
        chunks.append(" ".join(current))
    return chunks


def markdown_sections(text: str) -> list[tuple[list[str], str]]:
    """Split markdown by headings and remember the heading path, e.g. ['Billing', 'Refunds']."""
    sections, path, body = [], [], []
    for line in text.splitlines():
        m = re.match(r"^(#{1,6})\s+(.*)", line)
        if m:
            if "\n".join(body).strip():
                sections.append((path.copy(), "\n".join(body).strip()))
            level = len(m.group(1))
            path = path[:level - 1] + [m.group(2).strip()]
            body = []
        else:
            body.append(line)
    if "\n".join(body).strip():
        sections.append((path.copy(), "\n".join(body).strip()))
    return sections


@dataclass
class Chunk:
    id: str
    text: str        # what we embed / index (with a short context header)
    body: str        # the raw chunk text, for showing citations
    metadata: dict


def chunk_document(doc: Document, max_tokens: int = 200, overlap: int = 0,
                   add_header: bool = True, structure: bool = True) -> list[Chunk]:
    use_headings = structure and doc.source.endswith(".md")
    sections = markdown_sections(doc.text) if use_headings else [([], doc.text)]
    chunks = []
    for heading_path, section_text in sections:
        for i, body in enumerate(merge(split_text(section_text, max_tokens), max_tokens, overlap)):
            where = " > ".join(heading_path) or (f"page {doc.metadata['page']}" if "page" in doc.metadata else "")
            header = f"[{doc.source}{' | ' + where if where else ''}]\n"
            key = f"{doc.source}|{doc.metadata.get('page', '')}|{where}|{i}"
            chunks.append(Chunk(
                id=hashlib.sha256(key.encode()).hexdigest()[:16],   # same input -> same id on re-ingest
                text=(header if add_header else "") + body,
                body=body,
                metadata={**doc.metadata, "source": doc.source, "section": where, "tokens": n_tokens(body)},
            ))
    return chunks
```

One chunk it produces:

```text
647be736ae2bb59d {'source': 'handbook.md', 'section': 'Nimbus Cloud Support Handbook > Plans > Starter plan', 'tokens': 58}
[handbook.md | Nimbus Cloud Support Handbook > Plans > Starter plan]
The Starter plan costs 5 dollars per month. It includes 1 vCPU, 1 GB of RAM and 25 GB of SSD storage. ...
```

What each part does:

- **`split_text` is recursive.** It cuts on paragraphs first and only drops to lines, sentences and finally words for pieces that are still too long. Sentences stay whole whenever possible. LangChain's `RecursiveCharacterTextSplitter` uses the same idea. Now you know what it does inside.
- **`merge` packs pieces back up** to the size limit, with optional **overlap**: the last sentence or two repeat at the start of the next chunk, so a fact on a boundary isn't lost.
- **`markdown_sections` keeps structure.** A chunk never mixes "Refunds" with "Late payments", and it remembers its heading path.
- **The context header** (`[handbook.md | … > Starter plan]`) is a cheap version of Anthropic's contextual retrieval. A chunk that says only "It includes 1 vCPU…" now also carries *which* plan it's about. Anthropic's full version asks an LLM to write one or two sentences of context for each chunk. That costs more, but it works even when the document has no headings.
- **Stable IDs** come from source + page + section + position. Re-ingesting the same file produces the same IDs, so your vector database *updates* chunks instead of duplicating them.

## Measure, Don't Guess

The "right" chunk size depends on your documents and your questions. So build a small test set and measure. Here we write 12 realistic questions, each paired with a phrase the retrieved chunk must contain, and check whether keyword search (BM25, see [Hybrid Search](/docs/02-rag/hybrid-search)) finds it in the top 3:

```python
# eval_chunking.py — measure which chunk size actually retrieves the answer
import re

from rank_bm25 import BM25Okapi

from chunker import chunk_document
from ingest import load_folder

# question -> a phrase that must appear in a retrieved chunk for it to count as a hit
QUESTIONS = {
    "How long do I have to get my money back?": "within 14 days",
    "What happens to my server if my card keeps failing?": "suspended 14 days",
    "How many API calls can I make each minute?": "60 requests per minute",
    "How much RAM does the Pro plan have?": "8 GB of RAM",
    "Is incoming traffic charged?": "Inbound traffic is always free",
    "How often are encryption keys rotated?": "every 90 days",
    "When are customers told about a serious security incident?": "within 72 hours",
    "Which regions can I host my server in?": "Frankfurt, Singapore and Virginia",
    "How many snapshots can one server keep?": "up to 10 manual snapshots",
    "Does the cheapest plan come with backups?": "Starter does not include automatic backups",
    "Can I pay by bank transfer on a monthly plan?": "only available for annual contracts",
    "How quickly does support reply to Enterprise customers?": "within 30 minutes",
}
TOP_K = 3


def words(text: str) -> list[str]:
    return re.findall(r"[a-z0-9]+", text.lower())


def evaluate(max_tokens: int, overlap: int, structure: bool) -> tuple[float, int, int]:
    docs = load_folder("docs")
    chunks = [c for d in docs for c in chunk_document(d, max_tokens, overlap, add_header=structure, structure=structure)]
    bm25 = BM25Okapi([words(c.text) for c in chunks])
    hits, context_tokens = 0, 0
    for question, answer in QUESTIONS.items():
        scores = bm25.get_scores(words(question))
        top = sorted(range(len(chunks)), key=lambda i: scores[i], reverse=True)[:TOP_K]
        hits += any(answer in chunks[i].body for i in top)
        context_tokens += sum(chunks[i].metadata["tokens"] for i in top)
    return hits / len(QUESTIONS), len(chunks), context_tokens // len(QUESTIONS)


if __name__ == "__main__":
    print(f"{'strategy':<12} {'size':>5} {'overlap':>7} {'hit@3':>6} {'chunks':>6} {'tokens/question':>15}")
    for structure in (False, True):
        for size, overlap in [(32, 0), (64, 0), (64, 16), (128, 0), (256, 0), (512, 0)]:
            hit, n, ctx = evaluate(size, overlap, structure)
            name = "sections" if structure else "plain"
            print(f"{name:<12} {size:>5} {overlap:>7} {hit:>6.0%} {n:>6} {ctx:>15}")
```

The real output:

```text
strategy      size overlap  hit@3 chunks tokens/question
plain           32       0    58%     27              74
plain           64       0    92%     15             136
plain           64      16    92%     15             137
plain          128       0    92%      8             256
plain          256       0   100%      5             431
plain          512       0   100%      4             608
sections        32       0    83%     27              67
sections        64       0    92%     15             124
sections        64      16    92%     15             124
sections       128       0    92%     15             124
sections       256       0    92%     15             124
sections       512       0    92%     15             124
```

How to read it. Each of these lessons is general, not just about this corpus:

1. **Tiny chunks lose answers.** At 32 tokens, plain chunking finds only 58%. Answers get cut in half. Section-aware chunking holds up much better (83%) at the same size, because it never cuts across a heading.
2. **"100%" with big chunks is misleading.** At 512 tokens the whole handbook fits in four chunks, so of course the answer is "in" the top 3. But each question now sends **608 tokens** to the LLM instead of **124**. That's five times the cost, and lots of irrelevant text that can distract the model. Always track **context size** next to hit rate.
3. **Structure sets a natural size.** With sections, every size from 64 up gives identical chunks, because no section is longer than that. Good structure-aware chunking makes the size limit a safety net, not the main tool.
4. **Overlap didn't help here.** That matches Chroma's mixed results: overlap sometimes improves recall and always adds redundant tokens. Test it. Don't assume it.
5. **The one miss is a vocabulary problem, not a chunking problem.** Both strategies miss *"How long do I have to get my money back?"*, because the handbook says **"refund"** and keyword search can't match words that aren't there. No chunk size fixes this. **Embeddings** (semantic search) and **hybrid search** do.

On a real corpus, use 30–100 questions from real users or support tickets, and re-run this after every change to your ingestion pipeline.

## Mini Project: Ingest Your Own Docs

1. Collect 10–20 real documents: course notes, a product manual, your company wiki export. Include at least two PDFs.
2. Run `ingest.py` and **read** the cleaned text of three random pages. Fix what's broken: headers, tables, hyphenation.
3. Write 25 questions with expected answer phrases. Make half of them use *different words* than the documents.
4. Run the evaluation for plain vs section-aware chunking at 128, 256 and 512 tokens. Record hit@3 **and** tokens per question.
5. Pick a winner and save the chunks as JSON Lines (`id`, `text`, `metadata`). That file is the input for the next step: embedding and indexing.

**Stretch goals**

1. Replace BM25 with embeddings (see the next lesson) and check whether the "money back" question is now found.
2. Implement Anthropic-style contextual headers: ask an LLM for one sentence of context per chunk, then compare hit rates.
3. Add **incremental ingestion**: store a hash of each file and only re-chunk files whose content changed.

## Common Mistakes

1. **Never looking at the extracted text.** Most RAG bugs are ingestion bugs: scrambled tables, missing pages, headers in every chunk.
2. **Using a default chunk size without testing.** The best setting depends on your documents and questions. Measure it.
3. **Counting characters instead of tokens.** Limits, costs and embedding models are all token-based.
4. **Cutting across sections.** One chunk that is half "Refunds" and half "Late payments" matches both topics weakly.
5. **Dropping metadata.** Without source, page and section you can't cite answers, filter by document or debug retrieval.
6. **Random IDs.** Re-ingesting the same file then creates duplicates, and old versions keep showing up in answers.
7. **Judging by hit rate alone.** Bigger chunks always "contain" more answers. Track context tokens and answer quality too.

## Production Tips

- **Version your pipeline.** Store the chunker settings and a pipeline version with every chunk. When you change chunking, re-index everything and compare evals.
- **Keep the original text.** Embed the chunk with its context header, but show the raw `body` (with source and page) as the citation.
- **Handle updates and deletes.** When a document changes or is deleted, remove its old chunks by `source`, then insert the new ones. Stable IDs make this simple.
- **Respect permissions at ingestion time.** Store who may see each document in the chunk metadata, and filter on it at query time. Never rely on the LLM to hide private text.
- **Retrieve generously, then re-rank.** Anthropic found passing 20 chunks beat 5 or 10 in its tests. Combined with a re-ranker, good chunking plus wider retrieval is a strong default.
- **Consider no RAG at all for small corpora.** Anthropic notes that if your whole knowledge base is under about 200,000 tokens, you can simply put all of it in the prompt (with prompt caching to keep costs down).

## Key Takeaways

- Retrieval searches chunks, not documents, so ingestion quality caps RAG quality.
- Clean before you chunk: strip headers and footers, fix hyphenation, keep page numbers.
- Recursive, token-aware chunking along document structure is a strong default. Chroma found ~200-token recursive chunks consistently good.
- Add context (heading path or an LLM-written sentence) and stable IDs to every chunk.
- Measure hit rate **and** context tokens on real questions. Bigger chunks look better on hit rate but cost more and distract the model.
- Vocabulary mismatches ("money back" vs "refund") can't be fixed by chunking. You need embeddings or hybrid search for that.
